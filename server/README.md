# mad server

сервер алиасов и зашифрованной истории. node.js 24+, без npm-зависимостей. развёрнут на `https://sync.mad.tg`. бейджи на `https://b.mad.tg`. конфигурация и обслуживание описаны в [deploy](deploy/README.md).

## подключение текущего клиента

1. открой настройки mad → сервер → синхронизация истории. адрес `https://sync.mad.tg` уже подставлен; свой непустой адрес не заменяется.
2. нажми «открыть файл подключения» и выбери свой `connection.json`. подключение сохранится автоматически. если вставляешь json вручную, нажми «подключить».
3. нажми «сохранить файл переноса» и сохрани `mad-transfer.json` в защищённом месте. в нём мастер-ключ и токен доступа.
4. включи «для этого аккаунта» и нажми «закрыть». тумблер сохраняется сразу; повторно нажимать «подключить» не нужно.

на втором пк открой файл переноса с первого, а не первоначальный `connection.json`: исходный файл не содержит ключ расшифровки. оба клиента должны быть авторизованы в одном telegram-аккаунте. сервер не получает мастер-ключ. файл подключения выдан одному хранилищу; для другого аккаунта создай отдельное хранилище.

## запуск

задай `MAD_DATABASE` — абсолютный путь к sqlite вне репозитория. затем:

```powershell
node server/admin.mjs alias short real_username
node server/admin.mjs create-vault C:\private\mad-connection.json
node server/server.mjs
```

по умолчанию слушает только `127.0.0.1:8787`. перед доступом с другого пк нужен reverse proxy с https. не выставляй http-порт наружу. `MAD_HOST` и `MAD_PORT` меняют привязку.

в клиенте укажи https-адрес сервера, затем вставь содержимое файла подключения. ключ шифрования создаёт клиент; сервер его не знает. сохрани код переноса отдельно и включи синхронизацию только после этого.

для отдельного токена второго пк:

```powershell
node server/admin.mjs add-device C:\private\mad-second.json VAULT_ID second-pc
node server/admin.mjs devices VAULT_ID
node server/admin.mjs revoke-device TOKEN_HASH
```

второму пк нужны тот же мастер-ключ и vault, но его собственный token. перенос с прежним токеном тоже работает, однако отзыв такого токена отключит оба пк.

## протокол

`GET /v1/badges` совместим с tele: алиасы, пустые peers и notices, argon2-параметры. etag — sha256 точных байтов json в кавычках. алиасы меняются локальной командой администратора; публичного административного api нет.

`GET /v1/vaults/{vault}/events?after=0` возвращает ограниченную страницу событий. курсоры — десятичные строки, без округления 64-битных значений.

`POST /v1/vaults/{vault}/events` принимает `{ "events": [{ "id": "sha256", "blob": "base64" }] }`. требуется `Authorization: Bearer TOKEN`. токены хранятся только в виде sha256. хранилища изолированы, загрузка пакета атомарна, повтор одного события не создаёт копий. квота — 512 мб на хранилище, событие — до 2 мб, запрос — до 8 мб.

формат зашифрованного события: байт версии `01`, случайный nonce 12 байт, тег 16 байт, шифротекст. aes-256-gcm, ключ 32 случайных байта. aad — utf-8 `mad-history-v1:{vault}`. исходные account id, peer id, msg id и версии сообщений находятся внутри шифротекста. сервер видит размер, порядок событий, vault и соединения устройств. перенос шифротекста в другое хранилище не проходит проверку aad.

алгоритм использует [openssl evp aes-gcm](https://docs.openssl.org/3.5/man7/EVP_CIPHER-AES/); независимые проверки протокола используют [node crypto](https://nodejs.org/api/crypto.html). мастер-ключ не связан с api hash, паролем telegram или ключом mtproto.

отзыв токена запрещает будущие запросы, но не уничтожает уже скачанные копии и не делает известный устройству мастер-ключ неизвестным. при утечке ключа нужно новое хранилище с новым ключом. сервер не может восстановить потерянный ключ и не может гарантировать полноту истории, если администратор удалит данные; защита от отката новым устройством без ранее сохранённого курсора не реализована.

синхронизация переносит сохранённые сообщения, подписи и историю правок. локальные файлы медиа отдельно не загружаются. срок жизни ссылок на медиа telegram ограничен, поэтому доступность старых вложений на другом пк не гарантируется. очистка локальной истории не удаляет зашифрованный архив на сервере.

для резервной копии базы останови сервер и скопируй sqlite вместе с оставшимися `-wal`/`-shm` файлами либо используй штатный sqlite backup. не копируй только основной файл живой базы.

## проверки

```powershell
node --test server/server.test.mjs
```

проверяются шифрование и подмена, изоляция аккаунтов, отзыв доступа, дубликаты, etag, квота и точность курсоров. полноценный перенос между двумя авторизованными клиентами требует ручной проверки.
